1.Executive Summary

Turn a messy, one-paragraph creative brief from a busy marketer into a structured, validated, ready-to-use creative asset — with zero manual cleaning and the hard guarantee that bad data never flows silently downstream.

  • Agent 1 (Parser) extracts structured fields (campaign, audience, key message, tone, deadline).
  • A validation gate checks the output against a schema — retry → fallback → explicit error.
  • Agent 2 (Generator) produces creative output and only ever sees schema-valid data.

Provider-agnostic: deterministic offline "brain" by default (no API keys, ideal for demos/tests/CI); switchable to a hosted LLM via config.

2.Problem Statement

The business problem

  • Inconsistent — no shared template or field names.
  • Vague — "gen z", "kinda hype energy", "by friday" carry implicit meaning.
  • Incomplete — deadlines, names, audiences frequently missing.
  • Error-prone handoff — humans re-key fields; tools silently receive bad data.

The product problem

An AI that reads a brief and directly writes an ad will happily hallucinate on missing input — inventing a fake deadline, guessing the wrong audience — with no audit trail.

How we solve it

Separate "reading" from "writing", put a quality gate between them. Never guess business-critical facts; fill only safe gaps with recorded defaults; otherwise fail loudly with a structured error.

  "meta": { "provider": "local", "validation_attempts": 1,
            "repair_passes": 0, "fallbacks_applied": [] }
}

422 Unprocessable — two cases: (1) request-shape error (standard FastAPI detail); (2) business validation failure:

{
  "detail": {
    "error": "brief_validation_failed",
    "message": "Brief could not be validated after 3 attempt(s). Refusing to pass bad data...",
    "issues": [ { "field": "deadline", "message": "Field required", "value": null } ],
    "attempts": 3,
    "fallbacks_applied": ["tone defaulted to 'professional'", "..."]
  }
}

503 — configured LLM provider unreachable.

LOG_LEVELINFOLogging verbosity
PORT8000Server port (run.py)

Why two providers: local is deterministic (identical input → identical output, zero cost/network → reliable demos, CI, tests). openai runs the same code path (retry genuinely re-prompts with prior errors), so switching brains changes capability, not guarantees.

16.Brand-Guideline Enforcement v1.1 design

v1.0 enforces a built-in default brand voice. v1.1 proposes per-brand profiles wired through the same "no silent bad data" ladder.

16.1 What "brand guidelines" means here

Following brand guidelines = every output is on-brand (approved voice & tone), on-message (no banned/unapproved wording), and consistent (brand templates & vocabulary) — enforced as explicit, checkable rules, never a silent hope.

16.2 Already enforced today (v1.0)

LayerBrand guardrailLocation
Canonical Tone enumOutput limited to a fixed approved voice set (9)app/schemas/brief.py
TONE_SYNONYMSBrief language normalised to brand vocabularyapp/schemas/brief.py
_KEY_TEMPLATESDefault key messages are pre-approved on-brand copyapp/llm/local.py
_GEN_STYLECTAs & hashtags tone-flavoured, on-brandapp/llm/local.py
Validation gateLength, allowed tone, non-past deadlineapp/services/validation.py
RunMetaAudit trail of tone/defaults usedAPI response

16.3 Proposed: per-brand profiles (v1.1+)

  "brand_id": "techwear",
  "display_name": "TechWear Co.",
  "allowed_tones": ["hype", "edgy", "minimal"],   // reject others

17.Retraining & Continuous Learning v1.1 design

Honest framing: the default brain is rule/template based — no neural weights to "retrain" classically. So we define two learning regimes picked by data volume & active brain.

17.1 What "retrain" means in each regime

RegimeBrainWhat "retraining" isWhen to use
A · Rule curationlocalEdit & version knowledge tables/templatesDefault; determinism & auditability needed
B · Model tuningopenaiIn-context prompt updates → fine-tuningAccepted-example volume grows; richer language

17.5 Guardrails (non-negotiables)

  • Human approval gate before any rule/model promotion — no autonomous self-modification in v1.x.
  • Never train on unvetted output — only labelled, human-confirmed data.
  • Eval before promote — new rule/model must pass golden set + brand compliance or is rolled back.
  • Deterministic default stays — offline brain remains the CI/demo baseline.
  • Privacy — brand secrets / proprietary copy excluded from fine-tune corpora unless opted in.

Eval metricsParse accuracy · brand compliance · human acceptance · latency/cost
Who approves a release?Product/brand owner (rules) + engineering (tests, rollout)

19.Appendix — How to Run

🚫 Without AI (default — deterministic, offline)

python -m pip install -r requirements-dev.txt
python run.py                      # or: PORT=8001 python run.py
# Docs:   http://127.0.0.1:8000/docs    (or :8001)
# Health: http://127.0.0.1:8000/api/v1/health
python -m pytest                   # 17 tests

🤖 With AI (OpenAI — richer copy)

pip install -r requirements-optional.txt
# .env  (copy from .env.example):
LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o-mini     # optional
PARSER_RETRIES=2             # optional

python run.py                # restart → provider "openai"

Both modes share the same endpoint and the same validate → retry → fallback → error gate; only the underlying “brain” changes.
